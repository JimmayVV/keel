keel-reflect

Agentic memory for vanilla Claude Code — self-hosted, multi-machine, and unable to break your editor.

This is a plan for work that does not exist yet. keel today has the substrate for remembering and no mechanism for deriving. Everything below is the design for closing that gap, written so you can decide whether it's a weekend or a month before committing.

The one rule everything follows from

Recall is local file reads. Retain is remote LLM work. Never invert it.

Recall sits in the path of every prompt you type — it must be fast, offline-safe, and incapable of failing in a way you notice. Retain is derivation about the past — it can be slow, batched, and running on a machine that is currently switched off.

Invert this and your memory stops working when the homelab reboots. That isn't a memory system, it's a dependency. Every fault-tolerance property on this page is a consequence of that one rule.

Architecture: the repo is the bus

The container is not a service your machines call. It's another node on the same private git repo — a peer, not a dependency.

   desktop  ─────┐
                 │
   laptop   ─────┼──────►   data repo (private git)   ◄──────  reflect worker
                 │                                              (docker, homelab)
   work box ─────┘          keel/activity/*.jsonl   ──── reads ────►
    (separate                projects/*/memory/*.md ◄─── writes ────
     network)                notes/*.md

   recall  ──►  reads local markdown only.  never touches the network.
   retain  ──►  worker reads log, derives facts, commits markdown, pushes.

Your machines never open a connection to the container. They pull markdown from git at session start, same as they already do. The worker's output arrives as ordinary memory files — indistinguishable from notes you wrote yourself, except that they cite their evidence.

Fault tolerance: why this cannot brick Claude Code

FailureEffect on Claude CodeWhy
Container stopped / homelab powered offNoneLog keeps accruing locally; worker catches up on next run
Homelab destroyed permanentlyNone to past memoryEvery derived fact is markdown in git, already cloned to every machine. You lose future derivation only
You're on a plane / off-networkNoneRecall reads local files. You were never talking to the worker
Tailscale downNoneNot in the data path — see below
GitHub unreachableNone this sessionSync hook is bounded and fail-soft; local memory unaffected
Worker crashes mid-runNoneLog is append-only; worker is a consumer. Next run re-reads
Worker writes something wrongOne-line editIt's markdown in git. Delete the line, or git revert
Query-recall hook errors or hangsNoneReturns no context, turn proceeds. Ambient recall still works
The floor

If every single piece of this fails at once, what remains is: Claude Code reads the markdown files in your memory directory. That floor has no moving parts, no network, and no dependencies — and it's the behaviour you already have today.

Where Tailscale actually fits

You've called Tailscale the backbone, and I'd narrow that. For the data path it isn't needed — the worker reaches GitHub, your machines reach GitHub, and nothing listens on a port. Putting Tailscale in the data path would add a dependency for no capability.

Where it genuinely earns its place:

  • Operating the container — SSH in, read logs, check whether last night's run failed, restart it from a coffee shop.
  • If you later self-host the git remote instead of GitHub, the tailnet is how the laptop reaches it from outside the house.
  • If you run a local model for the retain step and want an inference endpoint reachable from anywhere without exposing a port.

Ops plane, not data plane. That distinction is what keeps the failure matrix above green.

Build walkthrough

1 Fact format not built

Before any container, decide what a derived fact looks like on disk. Everything else is plumbing around this.

---
claim: Prefers boring, well-understood solutions over clever ones
kind: derived            # observed | derived
confidence: 0.6
first_seen: 2026-07-12
last_seen: 2026-07-26
recurrence: 4
evidence:
  - 2026-07-12 keel: chose git over a custom sync daemon
  - 2026-07-19 scoresense: rejected the abstraction, kept duplication
  - 2026-07-26 keel: deferred Basic Memory rather than add a dependency
derived_by: keel-reflect
device: homelab
---

Across 6 sessions between Jul 12–26 you chose the simpler option four times when
a more capable one was on the table.

Why the front matter matters: kind separates observation from conclusion. evidence is what makes a claim challengeable from first principles — you can go read the sessions it came from. recurrence and confidence stop one fumbled sentence becoming a permanent belief about you. derived_by tells you at a glance whether you wrote it or a machine did.

2 Query recall via UserPromptSubmit not built

Build this before the worker. It's the half that must never break, it needs no container, and it's independently useful — it makes the memory you already write by hand surface at the right moment.

// hooks/recall.mjs — runs on every prompt. Local only. Fails to silence.
{
  "hookSpecificOutput": {
    "hookEventName": "UserPromptSubmit",
    "additionalContext": "Possibly relevant: <facts + citations>"
  }
}

Hard constraints: no network, no MCP call, a strict time budget, and any error path returns nothing rather than blocking the turn. Ambient recall (the memory index Claude Code loads natively) keeps working regardless.

3 The worker, run manually first not built

Before Docker, before cron — a script you invoke by hand and read the output of.

keel-reflect --since 7d --dry-run     # prints proposed facts, writes nothing

It reads keel/activity/*.jsonl (never transcript JSONL — undocumented and actively churned), passes it to a model, and emits candidate facts in the format above. Run it against a real week of your log. If the facts it proposes are wrong or banal, you've learned that for the cost of a script rather than a deployment.

This is the step that tells you whether the whole idea is worth it.

4 Idempotence and watermarks not built

The worker must never re-derive the same week twice, or your notes fill with near-duplicates that each look like independent evidence.

  • A watermark file in the repo records the last timestamp processed.
  • Re-running over an overlapping window updates recurrence and last_seen on an existing fact rather than writing a new one.
  • Facts are keyed by a stable slug so two machines can't create rival copies.

5 Containerise not built

Only now does Docker enter, and it stays boring: clone, run on a schedule, push.

services:
  keel-reflect:
    image: keel-reflect:local
    restart: unless-stopped
    environment:
      KEEL_DEVICE: homelab
      KEEL_DATA_DIR: /data
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY}
    volumes:
      - ./data:/data                       # the cloned data repo
      - ./ssh:/root/.ssh:ro                # deploy key, read-only

Credential scope matters. The container has write access to your memory. Use a GitHub deploy key scoped to that one repo, not a personal access token with account-wide reach. If the homelab is ever compromised, the blast radius should be a single repository.

Give it KEEL_DEVICE=homelab and a distinct git author, so you can always tell at a glance what you wrote and what it did.

6 Schedule, then leave it alone not built

Nightly is plenty. This is derivation about the past — there is no such thing as an urgent insight about last Tuesday. A run is: git pull → read log since watermark → derive → write markdown → commit → push. Your machines pick it up at the next session start.

Kill switch

Three levels, each one command, none requiring the container to be reachable:

KEEL_SYNC_OFF=1Stop syncing entirely. Local memory still works
docker stop keel-reflectStop deriving. Everything already derived stays
git revert <sha>Undo a bad batch of facts. It's just markdown in git

And the nuclear option, which is worth knowing exists: delete the container, delete the plugin, and your memory is still a directory of markdown files you can read with cat. Nothing here is stored in a format that requires keel to interpret it.

Suggested order

Steps 1–3 are the real project and can be done without Docker, Tailscale, or a homelab. They also answer the only question that matters: are the facts it derives any good? If the answer is no, you've spent an evening instead of a month. Steps 4–6 are deployment, and deployment is the easy part.
